# Code Review Deck

PR 의 코드 변경을 오프라인에서 발표·소개·리뷰할 수 있는 **슬라이드 덱**(단일 HTML)으로 만든다.
외부 CSS/JS/폰트/CDN 의존이 전혀 없어 파일 하나만 브라우저로 열면 동작한다.

## 왜 이 형태인가

리뷰어에게 코드를 "소개"할 때는 스크롤 문서보다 **한 화면에 한 논점**이 집중을 유지시킨다.
그래서 이 스킬은 발표 덱을 만든다. 검증된 CSS/JS 네비게이션 하네스를
`assets/deck-template.html` 로 번들해 두었으니, **매번 스타일을 새로 짜지 말고 그 템플릿을 복사해
슬라이드만 채운다.** 하네스가 이미 처리하는 것: 다크 테마, 진행바, 슬라이드 카운터,
키보드 네비(→/Space 다음, ← 이전, Home/End, F 전체화면), 화면 좌/우 클릭 이동, URL 해시 동기화.

## 워크플로

### 1. PR 메타 + diff 확보
- `gh pr view <PR>` 로 title·본문, JIRA(`CBRD-NNNNN`) 확보. 못 찾으면 사용자에게 확인.
- `gh pr diff <PR> --name-only` 로 실제 변경 파일 목록, `gh pr diff <PR>` 로 전체 diff 를 받아
  scratch 에 저장한다. **merge-base 가 오래되면 무관한 CI/빌드 churn 이 섞이므로,
  `gh pr diff` 가 잡는 PR 자신의 diff 를 진실로 삼는다.**
- base = `git merge-base HEAD origin/develop`(표기용), HEAD = PR.

### 2. 변경 파악 (함수 단위)
- diff hunk 를 함수/타입 단위로 훑어 변경 형태(신규 / 본문 변경 / 시그니처 변경 / rename /
  regression 수정 등)를 분류한다. 회귀 수정과 기능 변경을 구분해 둔다(색상이 달라진다).
- 시나리오가 있으면(PR 본문, repo 의 testcases/scenarios, `jira` 스킬) running example 로 잡는다.
  없으면 코드 실행 흐름으로 대체한다.

### 3. 슬라이드 설계 — 한 슬라이드 = 한 논점
기본 순서(내용에 맞게 가감):

1. **타이틀** — JIRA / PR / 한 줄 요약 + 변경 규모(N files, +X/-Y)
2. **문제 (AS-IS)** — 지금 왜 비효율/버그인가. 흐름 다이어그램.
3. **해결 (TO-BE)** — 무엇을 바꿨나. 대응되는 흐름 다이어그램.
4. **전체 흐름 / 진입점** — 외부 진입 → 핵심 함수 도달 경로.
5..N. **파일·함수별 핵심 변경** — AS-IS/TO-BE 코드 슬라이드. 실제 변수·함수명 그대로.
- **회귀 수정** — 함께 고친 기존 버그(있으면). 표로 정리, 회귀 색상.
- **핵심 불변식** — 리뷰 체크리스트(이것만 확인하면 되는 것들).
- **테스트 커버리지** — TC 파일/케이스 ↔ 검증 내용 표(있으면).
- **한 줄 요약** — 기억에 남길 한 문장 + 불변식 3줄.

### 4. 템플릿 채우기
`assets/deck-template.html` 를 출력 경로로 복사한 뒤 `<section class="slide">` 들을 실제 내용으로
교체한다. 템플릿 상단 주석의 슬라이드/박스 패턴(타이틀·흐름·코드·요약)과 클래스를 그대로 쓴다.
`<title>` 도 채운다. CSS/JS 는 건드리지 않는다.

### 5. 작성 규칙 (품질을 가르는 지점)
- **부등호 이스케이프**: 코드·다이어그램의 `<` → `&lt;`, `>` → `&gt;`. 안 하면 브라우저가
  태그로 먹어 다이어그램/코드가 깨진다(가장 흔한 실패). 화살표는 `&rarr; &larr; &darr;` 사용.
- **색상 코드 + 범례**: 신규=`add`(초록), 회귀수정=`reg`(앰버), 기존/AS-IS=`old`(회색),
  핵심 경로=`k`(accent). 템플릿의 `.legend` 를 남긴다.
- **실제 이름 그대로**: 변수·함수·타입명을 단축하지 말 것. 추가된 라인만 `<span class="add">`.
- **용어 통일**: 같은 개념은 덱 전체에서 하나의 표기로. (여러 표현이 섞여 있으면 하나로 정한다.)
- **자족성**: 외부 리소스 링크 금지. 모든 것이 이 HTML 안에 있어야 오프라인에서 열린다.

### 6. 검증 (브라우저 없이도)
완성 후 다음을 확인한다:
```bash
grep -c '<section class="slide">' <deck.html>            # 슬라이드 수 확인
python3 -c "from html.parser import HTMLParser; HTMLParser().feed(open('<deck.html>').read()); print('OK')"
# 태그를 깨뜨릴 수 있는 raw 부등호 잔존 점검 (식별자 사이의 < 또는 >)
grep -nE '[A-Za-z0-9_)]\s*<\s*[A-Za-z0-9_(]' <deck.html> | grep -v '&lt;'
```
파싱 OK, 슬라이드 수 일치, raw 부등호 0 이면 통과. 가능하면 실제 브라우저로도 넘겨 본다.

## 출력 경로
사용자가 지정하지 않으면 리뷰 대상과 같은 디렉토리에 `DECK.html`. (문서형 워크스루도 함께 만들면
`WALKTHROUGH.*` 와 나란히 둔다.)

## 함께 쓰는 스킬
- **code-review-walkthrough** — 좌측 목차가 있는 스크롤 문서형 워크스루(md). 덱과 상호보완.
  둘 다 필요하면 워크스루를 먼저 만들고 그 내용을 덱으로 압축하면 빠르다.
- **md2html** — 임의 markdown 을 좌측 목차 HTML 로. 발표 덱이 아니라 읽는 문서일 때.
