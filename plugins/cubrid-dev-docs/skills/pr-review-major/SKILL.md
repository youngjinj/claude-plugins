정작 결함은 "옮긴 값을 가리키는 쪽" 같은 좁은 질문에서 나온다.

## Step 0. 입력 수집

```bash
gh pr view <n> --json title,author,state,baseRefName,headRefName,additions,deletions,changedFiles,body,url
git fetch upstream                                   # 먼저. 낡은 ref 로 diffstat 을 내면 전부 틀린다
git log --oneline $(git merge-base HEAD develop)..HEAD
gh api "repos/CUBRID/cubrid/pulls/<n>/comments?per_page=100" \
  --jq '[.[].user.login] | group_by(.) | map({u:.[0], n:length})'
```

- [ ] 봇 리뷰(greptile 등)가 이미 있으면 **읽고 입력으로 삼는다.** 같은 것을 다시 찾지 않는다
- [ ] 커밋 메시지를 본문보다 먼저 읽는다 — 리뷰 대응 커밋일수록 최신이고 상세하다
- [ ] `cubrid-jira search CBRD-XXXXX`

## Step 1. 표본 선정 — 여기서 멈춘다

전수 대신 두 축만 고른다. 첫 축은 고정이고, 둘째 축은 리뷰 이력에 따라 갈린다.

```
  축 1  위험 최대     기존 동작을 건드리는 곳. blast radius 로 고른다

  축 2  리뷰 이력 없음   -> 신규 최대    이 PR 이 새로 쓴 코드가 가장 많은 곳
        리뷰 이력 있음   -> 미검토 최대  마지막 리뷰 코멘트 날짜 이후의 커밋이 만진 곳
```

**리뷰가 이미 붙은 PR 에서는 규모가 아니라 검토 공백이 옳은 축이다.**
이미 지적된 구역을 다시 읽으면 같은 결론에 도달하거나, 남의 지적을 다른 말로 반복한다.

```bash
gh api "repos/CUBRID/cubrid/pulls/<n>/comments?per_page=100" \
  --jq 'max_by(.created_at) | .created_at'          # 마지막 리뷰 시각
git log --format="%h %ad %s" --date=short --since=<그 날짜> --no-merges
```

고른 이유를 한 줄씩 대고 **사용자 확인을 받은 뒤 진행한다.**
이 정지가 없으면 전수 읽기로 미끄러진다.

결함 밀도가 높으면 표본을 넓히지 말고 그 사실 자체를 보고한다 — 분할 요청의 근거가 된다.

리뷰 이후 커밋이 **이전 리뷰 합의를 되돌렸는지**를 특히 본다.
저자가 지적을 받아 넣은 게이트를 다른 경로에서 우회하는 형태가 흔하다.

## Step 2. 관점 3회

표본에 대해 관점을 바꿔 세 번 돈다. 관점마다 결과를 분리해서 적는다.
같은 코드에서 서로 다른 결함이 나온다.

| 관점 | 질문 |
|------|------|
| tester | 이 변경의 TC 를 지금 쓸 수 있나. 못 쓰면 무엇이 없어서인가 |
| DBA | 오늘 이 기능을 쓰던 사람에게 무엇이 달라지나. 기본값은 |
| 유지보수 | 6개월 뒤 "단순화" 하려는 사람이 무엇을 깨나. 새 불변식은 적혀 있나 |

검증 비용이 큰 것은 직접 하지 말고 **저자에게 데이터 요구로 전환한다.**
정확도 비교표, 성능 수치, TC 추가는 저자의 몫이다.

## Step 3. 패러프레이즈 — 저자 검증용

이해한 동작을 자기 말로 풀어 쓴다. 이것은 리뷰 근거가 아니라
**"내가 이해한 것이 맞습니까" 를 묻는 문서**다.

저자는 설명하지 않고 듣는다. 두 모델이 갈리는 지점이 결함이다.
명세가 낡았을 때 이 패러프레이즈가 명세를 대신한다.

ASCII 다이어그램만 쓴다 (`-` `|` `+` `>` `<` `/` `\`). 라벨은 영어.

## Step 4. 규약 대조

기계적인 것만 본다. 명세가 낡아도 규약은 유효하다.

```
  에러 코드 추가        6곳 갱신했나
                        error_code.h / dbi_compat.h / en_US.msg / ko_KR.msg
                        / ER_LAST_ERROR / CCI base_error_code.h
  memory_wrapper.hpp    마지막 include + XXX 주석
  메모리                free_and_init. bare free 금지
  헤더 가드             _FILENAME_H_. #pragma once 금지
  빌드 모드             파서/옵티마이저는 #if !defined(SERVER_MODE)
```

사람이 볼 것은 **규약이 없던 영역에 새로 생긴 불변식**이다.
비트패킹 레이아웃, 두 자료구조가 필드를 공유하는 규칙 같은 것이 주석에 적혀 있는지 본다.

## Step 5. 보고 기준

아래 한 문장을 못 쓰면 버린다.

```
  누가 / 어떤 설정에서 / 무엇이 깨지는가
```

- 개수를 채우지 않는다. 0건도 결과다
- 심각도 태그를 제목 맨 앞에 둔다 — `[blocker] [high] [medium] [minor] [low] [question]`
- 근거 위치를 `파일:행` 으로 인용한다
- 연쇄를 번호로 끝까지 전개한다. "이상하다" 가 아니라 "그래서 무엇이 깨지는가"
- 확정과 확률을 나눈다
- CI 가 왜 못 잡는지 적는다 (기본값 OFF, 커버리지 공백)
- 같은 코드베이스의 올바른 선례를 인용한다 — 취향이 아니라 기존 계약 위반으로 만든다
- 저자 입장을 먼저 인정하고 꺾는다
- 항상 제안으로 닫는다. 대안을 둘 준다
- 비차단 의견은 `(nit)` 으로 분리한다

## 참고 A. 주장 층의 신선도

```
  코드 주석      가장 최신. 그 줄과 함께 쓰이고 함께 고쳐진다
  커밋 메시지    그 변경 시점. 리뷰 대응 커밋일수록 상세하다
  PR 본문        보통 최초 1회. 후반 커밋을 못 따라간다
  JIRA 명세      합의 시점. 가장 오래됨
```

어긋남의 **방향**이 판정 종류를 정한다.

| 어긋남 | 낼 것 |
|--------|-------|
| 코드 ↔ 코드 주석 | 확정 finding. 둘 중 하나가 결함이다 |
| 코드 ↔ 커밋 메시지 | 강한 finding. 그 커밋이 의도한 것을 못 했다 |
| 코드 ↔ PR 본문 | 본문 갱신 요청. major 아님 |
| 코드 ↔ JIRA 명세 | **미준수로 단정하지 않는다. 어느 쪽을 고칠지 묻는다** |

마지막 줄이 중요하다. 리뷰를 받아 저자가 고친 결과인 경우가 있고,
그때 갱신돼야 할 것은 JIRA 쪽이다.

## 참고 B. 층이 전부 낡았을 때 — diff 를 주장으로 읽는다

명세가 없어도 diff 는 항상 최신이다. hunk 마다 세 질문을 던진다.

```
  Q1  이 hunk 는 무엇이 틀렸다고 주장하는가        변경 이유
  Q2  같은 성질인데 안 바뀐 곳은 왜인가            일관성
  Q3  이 값을 가리키거나 의존하는 쪽은 갱신됐나    파급
```

**Q3 를 가장 오래 붙든다.** 결함은 거의 여기서 나온다.
값을 옮기는 변경이면 역포인터, 캐시 키, 백링크를 전부 찾는다.

## 참고 C. 함정

```
  낡은 ref        merge-base 전에 fetch 하지 않으면 diffstat 이 통째로 틀린다
  대소문자        grep 은 기본이 대소문자 구분이다. -i 없이 낸 근거는 무효일 수 있다
  도달 가능성     "게이트가 빠졌다" 는 지적 전에 그 경로에 값이 실리는지 확인한다
  실행 없는 예측  실행으로 뒤집힐 예측은 [예측] 으로 표기하고 확정처럼 쓰지 않는다
  테스트 러너     .queryPlan 같은 마커 파일이 암묵 설정을 만든다. 힌트 탓으로 돌리지 않는다
```
