이슈 하나를 JIRA/PR 로 낼 수 있는 상태로 만드는 문서 묶음을 쓴다.

**"산출물" 은 이 묶음을 가리키는 낱말이다.** 거기에 붙는 동사가 무엇이든 -- 생성, 작성,
정리, 최신화, 갱신, 보완 -- 이 규칙이 적용된다. 동사를 열거해서 맞추려 하지 말고, 대상이
이 묶음인지만 본다.

**평범한 파일 편집 요청처럼 들려도 대상이 이 묶음이면 이 규칙이 적용된다.**
`cbrd-*_issue.md`, `*_pr.md`, `*_design_*.md`, `*_test_*.md`, `*_deferred_*.md` 를
건드리는 모든 작업이 그렇다 -- 새로 쓰는 것과 이미 있는 것을 다듬는 것에 같은 규칙을 쓴다.

**"줄바꿈만 고쳐줘", "이 문장만 다듬어줘" 처럼 범위가 좁아도 마찬가지다.** 좁은 요청이
규칙을 면제하지 않는다. 한 줄을 고치면서 `_issue.md` 와 `_issue.jira` 의 문장 짝이나 JIRA
문법을 깨뜨리는 일이 실제로 생긴다.

$ARGUMENTS

문서를 새로 쓸 때도, 이미 있는 묶음을 점검할 때도 같은 규칙을 쓴다.
개별 문서의 문체는 `tight-comments`, JIRA 본문은 `jira-create-imprv`/`jira-create-error`,
PR 본문은 `git-create-pr` 을 따른다. 이 스킬은 **묶음 전체의 구성과 경계** 를 정한다.

## 품질 기준 -- 배포 품질이 기본값

**이 묶음은 처음 쓸 때부터 배포 품질이어야 한다.** 초안으로 두고 나중에 다듬는 것이 아니다.
JIRA 첨부와 PR 본문은 올리는 순간 남이 읽고, 올린 뒤에 고쳐도 이미 읽은 사람의 이해는
고쳐지지 않는다.

**판정 기준은 하나다 -- 이 묶음을 받은 사람이 이 대화 없이 읽을 수 있나.** 첨부만 내려받은
사람, 이 저장소가 없는 사람, 이 대화를 보지 못한 사람이 기준이다. 문서 하나가 다른 문서의
근거까지 담아야 한다는 뜻은 아니다 -- 상세도 계층(2절)은 그대로다. 각 문서가 **자기 역할에
대해** 완결되면 된다.

**`deferred_*.md` 도 같은 기준을 지킨다.** 첨부하지 않지만 배포 품질은 유지한다. 읽는
사람이 JIRA 수신자가 아니라 **나중에 그 방향을 다시 꺼낼 사람** 이라는 것만 다르고, 기준은
같다. 그 사람도 이 대화를 보지 못한다.

접은 작업을 적는 것과 작업 기록을 남기는 것은 다르다. **접은 방향의 상태와 결론은 끝난
판단이므로 아래 표에 걸리지 않는다.** 보류라는 상태, 구현/측정하지 않았다는 사실, 옛 측정치
의 출처는 모두 결론이다. 걸리는 것은 그 판단에 이르는 과정을 늘어놓는 것이다 -- "처음에는
이렇게 해 봤다", "그때 스크립트에는 그 단계가 없었다" 가 그렇다.

배포 품질이 아닌 것은 대개 이렇다.

| 남아 있으면 실격 | 왜 |
|---|---|
| 작업 기록과 회고 -- "이번에 돌려 봤더니", "그 단계가 없었다" | 읽는 사람이 알고 싶은 것은 무엇을 해야 하는가다. 실행할 때마다 낡는다 |
| 문서가 자기 목적을 설명하는 문장 -- "이 절은 ... 를 짚는다" | 절의 내용이 그 일을 하면 된다. 하겠다고 적는 것은 내용이 아니다 |
| 같은 층의 산출물 md 를 서로 가리키는 것 | 하나만 받은 사람이 읽을 수 없다. 테스트 케이스와 스크립트 이름은 적어도 된다 -- 6절이 경계를 갖는다 |
| 미완성 표시 -- TODO, 확인 필요, 추후 보완 | 판단을 읽는 사람에게 넘기는 것이다. 판단이 끝나지 않았다는 **결론** 은 이것이 아니다 |
| 움직이는 식별자, 깨진 JIRA 문법 | 올린 뒤에 낡거나 렌더링이 깨진다 |
| 나만 아는 축약, 이 대화에서만 통하는 지시어 | 맥락이 없는 사람에게는 읽히지 않는다 |

**"일단 이렇게 두고 나중에" 가 없다.** 지금 판단할 수 없는 것은 비워 두는 것이 아니라,
**판단할 수 없다는 것과 무엇이 있어야 판단되는지를 결론으로 적는다.** 재지 못한 측정,
덮지 못한 축, 찾지 못한 도입 근거가 그렇다. 그렇게 적은 것은 배포 품질이고, TODO 로 남긴
것은 아니다.

올리기 전에 훑는 축은 10절이 갖는다.

## 누가 읽는가

**준개발자다.** 이 코드를 매일 보는 사람이 아니라, 기술 용어는 알지만 이 모듈은 처음 보는
사람이다. 네 문서 전부에 해당한다.

**용어는 기술 용어로 쓰고, 문장은 최대한 쉽게 쓴다.** 함수 이름/플래그 이름/자료구조 이름은
그대로 적는다. 바꾸면 코드에서 찾을 수 없다. 대신 **그것이 무슨 일을 하는지는 풀어서 적는다.**
"시험" 대신 "테스트" 처럼, 읽는 사람이 실제로 쓰는 말을 고른다.

문장이 어려워지는 자리는 대개 정해져 있다.

| 증상 | 고치는 법 |
|---|---|
| 한 문장에 절이 셋 넘게 붙는다 | 문장을 나눈다. 근거가 둘이면 문장도 둘이다 |
| 근거를 여럿 한 문장에 넣었다 | "이유가 둘이다. 첫째 ... 둘째 ..." 로 번호를 붙인다 |
| 주어가 "그 값", "그 신호" 처럼 앞을 되짚어야 안다 | 무엇인지 이름으로 다시 적는다 |
| 수를 먼저 말하고 항목은 나중에 나온다 -- "두 경우가", "세 가지를" | 그 자리에서 항목을 보여 준다. 같은 문장, 바로 다음 목록, 표 중 하나 |
| 비유어를 쓴다 -- 태운다, 밟는다, 찍는다, 잡는다, 샌다 | 그 동작의 기술 용어로 바꾼다 |
| 축약어를 풀지 않는다 -- UB, TU | 처음 나올 때 풀어 쓴다 |
| 사실만 나열하고 끝난다 | 그래서 무엇을 하라는 것인지 마지막에 적는다 |

**핵심만 적어도 된다.** 짧아서 부족한 문서보다, 길어서 안 읽히는 문서가 더 자주 실패한다.

## 코드 블록

**언어를 지정한다.** ` ```c `, ` ```sql `, ` ```sh `. 의사코드도 C 꼴이면 `c` 로 적고 주석은
`/* */` 를 쓴다 -- `#` 은 C 하이라이팅에서 전처리기로 잡힌다. 순수 ASCII 그림에는 지정하지
않는다.

**한글이 열을 밀어낸다.** 한글은 동아시아 환경에서 두 칸으로 그려지므로, 한글 **뒤에**
정렬해야 할 열이 오면 그 열이 어긋난다. 다음 두 규칙으로 막는다.

- **그림의 라벨은 영어로 쓴다.** 한글 설명은 그림 밖에 따로 둔다
- **의사코드의 한글 주석은 코드 위 줄에 둔다.** 꼬리에 붙여 여러 줄을 맞추려 하지 않는다

한글이 줄 **끝** 에만 있으면 괜찮다. 뒤에 맞출 것이 없기 때문이다.

**표로 쓸 수 있으면 표로 쓴다.** 두 열짜리 대조를 코드 블록에 공백으로 맞춰 넣으면, 값이
바뀔 때마다 다시 정렬해야 하고 한글이 섞이면 그마저 어긋난다.

**본문도 ASCII 와 한글만 쓴다.** 다이어그램만의 규칙이 아니다. 폭이 모호한 문자(`--` 대신
em dash, `/` 대신 가운뎃점, `^2` 대신 위첨자, `->` 대신 화살표)는 동아시아 환경에서 두 칸으로
그려져 **표의 열이 어긋난다.** `_issue.jira` 는 어차피 ASCII 로 쓰게 되므로, `_issue.md` 도
같이 맞춰야 두 파일이 어긋나지 않는다.

| 쓰지 않는다 | 대신 |
|---|---|
| em dash | `--` |
| 가운뎃점 | `/` |
| 위첨자 | `^2` |
| 화살표 | `->` |

한 줄로 확인할 수 있다 -- 한글과 ASCII 가 아닌 문자를 세어 0 이면 된다.

## 1. 디렉터리

```
<analysis-dir>/issues/cbrd-#####_<topic>/
  cbrd-#####_issue.md                   JIRA 본문의 리뷰용 Markdown. design 의 축약
  cbrd-#####_issue.jira                 JIRA 붙여넣기용. `_issue.md` 와 같은 내용을 JIRA wiki 로
  cbrd-#####_pr.md                      GitHub PR 본문. issue 의 축약
  cbrd-#####_design_YYYYMMDD_HHMM.md    JIRA 첨부. 이 이슈의 상세 전부
  cbrd-#####_test_YYYYMMDD_HHMM.md      JIRA 첨부. TC 를 어떤 범위로 설계할지
  cbrd-#####_deferred_YYYYMMDD_HHMM.md  (있을 때만) 접은 다른 해결 방향. 첨부하지 않는다
  cbrd-#####_testcases_YYYYMMDD_HHMM/   JIRA 첨부. zip 으로 묶어 올린다
    cases/   cbrd-#####_testcases_NN.sql
    scripts/ cbrd-#####_testcases_NN.sh       (셸이 필요할 때만)
    answers/ cbrd-#####_testcases_NN.answer
    README.md                           첨부에서 뺀다. 아래 항목을 담는다
  NNNN-<subject>.patch                  git format-patch. 첨부하지 않는다 -- PR 이 갖는다
```

**디렉터리와 그 안의 모든 것에 이슈 번호를 앞에 붙인다.** 이유가 자리마다 다르다. JIRA
첨부는 내려받으면 한 폴더에 섞이므로 `design_...md` 만으로는 어느 이슈 것인지 알 수 없다.
첨부하지 않는 `issue.md`, `pr.md` 도 여러 이슈를 한 편집기에 열어두고 오가는 동안 탭
이름만 보이므로 같은 문제가 생긴다. 디렉터리 이름도 `NN-<topic>` 대신 번호를 쓴다 --
순번은 분석 문서 안에서만 뜻이 있고, JIRA/PR 로 넘어가면 아무 것도 가리키지 않는다.

**아직 번호를 못 땄으면 `wip_` 를 쓴다.** `wip_issue.md`, `wip_design_...md` 처럼
같은 자리에 같은 방식으로 붙인다. 번호가 나오면 한꺼번에 바꾼다. 접두사 없이 두면 나중에
붙일 때 무엇이 빠졌는지 알 수 없고, 임시 이름을 따로 만들면 규칙이 둘이 된다.

**시각은 디렉터리에 붙이고 안의 파일은 되풀이하지 않는다.** 디렉터리째 묶어 올리므로 버전은
그 이름 하나로 정해진다. 안의 파일까지 시각을 달면 내용이 안 바뀌어도 이름이 흔들린다.

**테스트케이스 README 가 답해야 하는 것.**

| 항목 | 왜 |
|---|---|
| 어떤 DB 문자셋이 필요한가 | 답안이 문자셋에 매인다 |
| 답안을 **어느 빌드로** 만들었는가 | 변경 전이 기준인지 변경 후가 기준인지 |
| 변경 전에 실패해야 정답인 케이스가 있는가 | 결함을 고치는 이슈는 기준이 뒤집힌다 |
| 출력 비교인가 종료 상태 판정인가 | 셸 케이스는 후자인 경우가 많다 |
| 무엇으로 돌리는가 | CTP, 별도 하네스, 직접 실행 |
| `test_*.md` 의 어느 축을 덮는가 | 축 이름으로 대응시킨다. 절 번호는 옮기면 낡는다 |
| 덮지 못하는 축과 그 이유 | 없으면 다음 사람이 커버된 것으로 읽는다 |

**그 이슈에 딸린 문서는 그 이슈 디렉터리에 둔다.** 분석 루트에 두면 어느 이슈의 것인지 잃는다. 첨부하지 않는 문서도 마찬가지이고, 첨부 여부는 이슈 머리말에서 밝힌다.

**파일명 시각은 `_YYYYMMDD_HHMM` 하나로 통일한다.** 날짜만 쓰다가 나중에 시각을 붙이면
JIRA 첨부를 전부 지우고 다시 올려야 한다.

**시각은 첨부물마다 따로 매긴다.** 그 첨부물의 내용을 마지막으로 고친 시각이다. 문서만 고쳤으면
테스트케이스 디렉터리 이름은 그대로 둔다 -- 안 바뀐 것을 다시 올릴 이유가 없다. 한 번에 여러
첨부물을 고쳐 함께 올릴 때는 같은 시각으로 맞춘다.

## 2. 상세도의 계층

`design` -> `issue` -> `pr` 은 **같은 내용을 점점 줄인 것** 이다. 서로 다른 내용을 담는 것이
아니다.

| 문서 | 분량 | 답하는 것 |
|---|---|---|
| `design_*.md` | 전부 | 대상 코드의 구조, 문제의 기전, 변경마다의 결정과 근거, 동작이 달라지는 지점, 성능 |
| `issue.md` | `design` 의 축약 | 왜 이 이슈를 하는가, 문제가 무엇인가, 어떤 개선으로 어떤 결과가 났는가, 무엇을 바꾸는가, 어떤 분야의 테스트가 필요한가 |
| `pr.md` | `issue` 의 축약 | 왜 이 PR 인가, 효과가 무엇인가, 어디를 바꿨는가 |

`test_*.md` 는 이 계층 밖의 축이다 -- 6절. `deferred_*.md` 도 밖이다 -- 7절.

계층이 적용되는 것은 **핵심 주장** 이다 -- 문제가 무엇인가, 무엇을 바꾸는가, 동작이 어떻게
달라지는가, 효과가 무엇인가.

- 핵심 주장은 위로 갈수록 짧아질 뿐 **없어지거나 달라지지 않는다.** 짧은 쪽에만 있는
  핵심 주장이 있으면 긴 쪽이 비어 있는 것이다
- **줄이되 바꾸지 않는다.** 세 문서가 같은 사실을 서로 다르게 말하면 어느 것이 맞는지 알 수 없다
- 줄일 때 버리는 것은 **근거와 기전** 이다

계층 밖인 것도 있다. 문서마다 제 역할에서 나오는 것들이고, 위로 옮기지 않는다.

| 문서 | 그 문서에만 있어도 되는 것 |
|---|---|
| `design` | 근거, 기전, 실패 처리의 세부, 측정 전부 |
| `issue` | JIRA 양식이 요구하는 절 (Specification Changes, A/C, DoD) |
| `pr` | 리뷰 캐비앳 -- diff 에 안 보이지만 리뷰어가 알아야 할 것 |

**단, 캐비앳이 밖에서 보이는 동작이나 안전성을 바꾸는 것이면 핵심 주장이다.** 그때는
`issue` 와 `design` 에도 있어야 한다.

**변경을 몇 갈래로 세는지 세 문서가 어긋나면 안 된다.** `design` 이 넷으로 쓰고 `issue` 가
여섯으로 쓰고 `pr` 이 넷으로 쓰면, 읽는 사람은 어느 문서가 범위를 빠뜨렸는지 알 수 없다.
묶기로 했으면 세 문서를 같이 묶는다.

**다르게 세도 되는 경우가 하나 있다** -- 묶는 잣대가 문서마다 다를 때다. `design` 이 설계
갈래로 셋을 세고 `issue` 와 `pr` 이 밖에서 보이는 변경 하나로 묶는 것이 그렇다. 그때는
**묶었다는 것을 긴 쪽이 말해야 한다.** 말하지 않으면 빠뜨린 것과 구별되지 않는다.

**딸린 것은 갈래로 세지 않는다.** 개명 때문에 옛 이름의 마지막 호출부를 옮긴 것, 변수
이름을 의미에 맞게 바꾼 것은 그 갈래 안의 항목이다. 따로 세면 갈래 수가 부풀고, 리뷰어는
독립된 변경이 그만큼 있는 것으로 읽는다.

**목록이 다섯을 넘으면 서브 카테고리로 묶을지 검토한다.** 항목이 쭉 나열되면 어디까지가
한 덩어리인지 안 보이고, 읽는 사람이 전체를 머리에 담아야 한다. 묶을 잣대를 찾아본다 --
무엇을 바꾸는 변경인지, 어느 계층을 건드리는지, 어떤 문제에 대응하는지. **잣대가 없으면
평면으로 둔다.** 억지로 묶으면 이름만 붙은 껍데기가 생기고, 그것이 나열보다 나쁘다.

**한 갈래의 항목이 셋을 넘으면 한 겹 내린다.** 최상위 항목은 **무엇을 바꿨나** 하나만
말하고, 세부와 근거는 하위 항목으로 내린다. 평면으로 쭉 나열하면 어느 것이 변경이고 어느
것이 그 변경의 설명인지 구별되지 않는다.

두 규칙의 순서가 있다. **먼저 다섯을 넘는지 보고 묶을지 정하고, 그 다음 각 묶음 안에서
셋을 넘는지 보고 깊이를 정한다.** 순서를 바꾸면 깊이를 준 뒤에 다시 묶게 되어 두 번 고친다.

`pr.md` 는 축약이라 `issue` 와 겹치지만, **JIRA 본문을 그대로 옮기지 않는다.** 리뷰어가
diff 를 열기 전에 알아야 할 만큼만 남긴다.

**`Purpose` 는 `Implementation` 의 모든 항목을 설명해야 한다.** 변경이 여럿이면 근거도
여럿이다. 하나만 적으면 나머지 항목이 왜 이 PR 에 있는지 알 수 없고, 리뷰어는 범위가
넘친 PR 로 읽는다. 원인이 여럿이어도 대개 한 가족이다 -- 그 공통점을 한 문장으로 적고
갈래를 붙인다.

**낱말을 셋으로 가른다.** "효과" 한 낱말로 묶으면 규칙이 서로 부딪힌다.

| | 무엇 | 어디 |
|---|---|---|
| **비효율** | 지금 무엇이 쓸데없이 일어나는가 | `Purpose` 여는 부분 |
| **해소** | 그 비효율 중 무엇이 없어지는가 | `Purpose` 닫는 문장 |
| **성과** | 얼마나 좋아지는가. 수치, 배수, 비율 | `issue` 와 `design` 만 |

**`Purpose` 는 "어떤 비효율을 없앤다" 가 되어야 한다.** 비효율을 적고 해소로 닫는다.
**성과는 여기가 아니다** -- 얼마나 느린지, 몇 배 빨라지는지는 `issue` 와 `design` 이 갖는다.
문장이 "~로 늘어난다" 로 시작하거나 "~가 된다" 로 끝나면 대개 성과를 적은 것이다.

**닫는 문장은 새 코드를 서술하는 것이 아니라 해소를 말한다.** 무엇을 하게 되는지만 적으면
사실 적시로 끝나고, 앞에서 든 비효율 중 무엇이 없어지는지가 남지 않는다. 앞의 비효율을
목적어로 받아 없앤다 / 건너뛴다 / 줄인다 로 닫는다. 비효율을 여럿 들었으면 닫는 문장이
그 전부를 받는지 센다.

| 사실 적시 | 해소 |
|---|---|
| 타입이 맞는 값은 구조체 복사로 넘긴다 | 구조체 복사로 넘겨 **이 절차를 통째로 건너뛴다** |
| 센 값을 캐시에 되쓰게 한다 | 캐시에 되써 **같은 값을 다시 스캔하지 않게 한다** |

**`Remarks` 는 코드 주석의 여집합이다.** 항목마다 같은 사실이 코드 주석에 이미 있는지 보고,
있으면 뺀다 -- 리뷰어는 그 주석을 diff 에서 함께 읽는다. 설계 배경도 뺀다. `design` 이 갖는다.
남는 것은 **코드를 읽어서는 알 수 없는데 리뷰에 필요한 것** 뿐이고, 대개 이런 것들이다.

| 남길 것 | 왜 |
|---|---|
| 밖에서 보이는 동작이 달라지는 지점 | 리뷰어가 스스로 찾아내기 가장 어렵고 놓치면 가장 비싸다 |
| 새 코드가 **여전히 못 하는 것** | diff 는 무엇이 좋아졌는지만 보여 준다. 어디까지만 좋아졌는지는 안 보인다 |
| 조건 하나가 그 자리에 있는 이유 | 주석에 없다면 다음 사람이 지운다 |

항목당 한두 문장이다. 길어지면 `design` 으로 옮기고 여기서는 가리키지도 않는다.

**`Implementation` 과 `Remarks` 는 `Purpose` 를 되풀이하지 않는다.** `Implementation` 은
**어디를 어떻게 고쳤고 왜 그래도 되는지**, `Remarks` 는 **리뷰어가 조심할 것** 이다.
"분명해진다", "그 경로가 없어진다" 처럼 좋아졌다고 다시 말하는 문장이 성과의 되풀이다.

**그 변경이 없애는 직접 비용은 구현 설명에 필요하다.** "`strcat` 을 없앤다" 보다
"`strcat` 이 덧붙일 때마다 문자열 끝을 다시 찾던 것을 없앤다" 가 낫다. 무엇을 고쳤는지가
그 문장에서 끝나기 때문이다. 금지되는 것은 PR 전체의 성과를 다시 말하는 것이지, 그 줄이
없애는 연산을 적는 것이 아니다.

**`Remarks` 는 방향을 돌려 적는다.** "그 실패가 이제 전파된다" 는 성과이고, "이 실패는
여전히 전파되지 않는다" 는 캐비앳이다. 같은 사실이라도 뒤엣것만 리뷰에 쓸모가 있다.

**성과를 세 문서가 다르게 적는다.**

| 문서 | 성과를 어떻게 적나 |
|---|---|
| `design` | 측정치 전부. 성능 절 한 곳에 모은다 |
| `issue` | 무엇이 얼마나 좋아졌는지. 대표 수치 한둘까지 |
| `pr` | 적지 않는다. `Purpose` 의 해소 문장이 정성적으로 말하는 것으로 끝이다 |

**측정에서 출발한 이슈가 아니면 수치를 넣지 않는다.** 구조적/논리적 비효율을 코드에서
읽어내 만든 이슈라면 무엇이 왜 비효율인지로 충분하고, 없는 측정을 만들어 붙이지 않는다.

**어림값은 어림이라고 쓴다.** 계산으로 낸 수치를 측정치와 같은 표에 두면 둘 다 실측으로
읽힌다. `*위 수치는 측정이 아니라 <무엇>으로부터의 어림이다.*` 한 줄이면 된다.

### 2.1 측정치를 인용할 자격

측정한 수치라도 다 인용할 수 있는 것은 아니다. 셋을 확인한다.

| 확인 | 기준 |
|---|---|
| build 짝이 맞나 | baseline 은 **그 브랜치의 merge-base** 여야 한다. 오래된 develop 커밋을 쓰면 무관한 변경이 섞인다 |
| 짝이 맞는지 어떻게 아나 | 이 변경이 비용을 더하지 않는 **no-op 조건** 에서 두 build 를 먼저 잰다. 거기서 큰 차이가 나면 수치보다 build 짝을 먼저 의심한다 |
| 그 셀을 인용할 수 있나 | 같은 셀 반복 측정의 min-max 폭을 **함께 밝힌다.** 그 폭이 주장하려는 개선율을 넘으면 그 셀로 개선율을 주장하지 않는다 -- 방향까지 부정하는 것은 아니고, 크기를 인용하지 않는 것이다 |

**구조적 지표를 함께 잡아 둔다.** 처리량은 장비 부하에 흔들리지만, syscall 횟수나 호출
횟수처럼 코드 구조에서 나오는 값은 **훨씬 덜 흔들린다.** 그 지표가 있으면 처리량을 인용할
수 없는 환경에서도 주장의 기전은 확인된다. **이슈가 주장하는 것을 구조적 지표로 표현할
수 있는지** 먼저 보고, 되면 그것을 판정 지표로 삼는다.

**다만 구조적 지표가 처리량의 대체는 아니다.** 호출이 줄었다는 것과 그래서 얼마나
빨라진다는 것은 다른 주장이다. 구조적 지표만 있으면 **줄었다는 것까지만** 적는다. 그 값도
동시성과 buffer 경계와 재시도에 따라 달라질 수 있으므로, 무엇을 고정하고 잰 것인지 함께
적는다.

**재측정이 환경 때문에 안 되면 옛 측정치를 지우지 말고 출처를 밝힌다.** 잰 시점과 그때의
build 짝을 적어 두면 낡지 않는다 -- 그 짝은 역사적 사실이라 나중에 merge-base 가 움직여도
틀리지 않는다.

**단, 위 표를 통과한 측정치만 그렇다.** build 짝이 어긋났거나 변동 폭이 개선율보다 컸던
수치는 시점을 적어도 인용할 수 있는 증거가 되지 않는다. 그때는 수치를 빼고 **재지 못했다는
것과 무엇이 있어야 재는지** 를 적는다.

## 3. issue 는 두 파일이다

같은 내용을 두 벌로 쓴다. `_issue.md` 는 리뷰용 Markdown 이고 `_issue.jira` 는 JIRA 에
붙여넣는 wiki 문법이다. **한 파일 안에 두 벌을 넣지 않는다** -- 한쪽 문법 검사를 돌릴 때마다
다른 쪽이 전부 걸리고, 편집기에서 어느 벌을 보고 있는지 헷갈린다.

`_issue.md` 는 이렇다.

```markdown
# <영문 제목 -- PR 제목과 같은 문자열>

> JIRA [CBRD-#####](...) / 브랜치 `CBRD-#####` / 배경과 설계 근거는 `design_*.md`, 검증 방법은 `test_*.md` 와 `tc/` 가 갖고 둘을 첨부한다.

---

## Description / Specification Changes / Implementation / Acceptance Criteria (A/C) / Definition of done (DoD)
```

`_issue.jira` 는 이렇다. 파일 맨 위 세 줄은 붙여넣는 사람을 위한 안내이고 JIRA 에 넣지 않는다.

```text
이 파일은 JIRA 7 자체 호스팅 문법으로만 적는다. Markdown 문법을 쓰지 않는다.
가로줄 위 마지막 줄이 제목이고 Summary 필드에 넣는다. 가로줄 아래가 본문이고 Description 필드에 붙여넣는다.
본문은 h2. *Description* 으로 시작하지 않는다. 그 필드 제목과 겹친다.

<영문 제목 -- _issue.md 의 H1 과 같은 문자열>

----

<본문>
```

제목은 `git-create-pr` 의 PR 제목과 같은 문자열로 맞추되, **`[CBRD-#####]` 접두사는
GitHub 제목 필드에만 붙인다.** `_issue.md` 의 H1 과 `_issue.jira` 의 제목 줄은 접두사 없는
본문이다.

`_issue.md` 의 머리말은 `---` **위** 에 둔다. JIRA 에 옮기지 않는 자리이므로 파일
경로와 브랜치명 같은 내부 정보를 여기에 쓴다.

**두 파일을 함께 고친다.** `_issue.md` 만 고치고 `_issue.jira` 를 두면 다음에 붙여넣을 때
옛 내용이 올라간다. 아직 `_issue.jira` 를 만들지 않았으면 `_issue.md` 가 확정된 뒤에 한
번에 옮긴다 -- MD 가 흔들리는 동안 두 벌을 따라 고치면 줄 구조가 어긋난다.

JIRA wiki 주의. **아래는 CUBRID JIRA 인스턴스에서 실제로 깨지는 것을 보고 적은 것이다** --
Atlassian 문서의 일반 규칙이 아니고, renderer 버전과 붙여넣기 경로에 따라 달라질 수 있다.
새 환경에서는 확인하고 쓴다.

- **`{{...}}` 가 렌더링되지 않는다.** monospace 를 뜻하는 문법이지만 이 인스턴스에서는
  중괄호가 그대로 출력된다. 쓰지 않는다
- 코드 펜스 대신 `||헤더||` 표를 쓴다. MD 쪽은 코드 블록이어도 된다
- 굵은 글씨는 `*text*`, 마크다운 `**text**` 는 그대로 출력된다
- **`*` 의 바깥쪽에 글자나 숫자가 붙으면 굵게가 적용되지 않는다.** 한글도 글자다. 그래서
  `한글*강조*한글` 은 굵어지지 않고 별표가 그대로 보인다. 여는 `*` **앞** 과 닫는 `*`
  **뒤** 가 공백이나 문장 부호여야 한다
- 그래서 **조사가 문제가 된다.** `*강제*되므로` 가 실패한다. 굵게 할 범위를 어절 끝까지
  넓히거나(`*강제되므로*`), 문장을 나눠 굵은 부분이 공백이나 줄 끝 앞에서 닫히게 한다
- 마침표와 쉼표는 괜찮다. `*강제*.` 는 정상이다. 괄호와 매크로 경계(`{color}` 등)는
  확인하고 쓴다 -- 문자 종류만으로 정해지지 않는다
- **`#` 목록 항목 사이에 빈 줄을 넣으면 채번이 1 로 돌아간다.** 빈 줄이 목록을 끊어 새
  블록으로 만든다. 항목을 빈 줄 없이 붙여 쓴다
- **`h2.` 앞에 빈 줄을 둔다.** 이 인스턴스에서는 앞 문단에 바로 붙이면 제목으로 렌더링되지
  않았다
- **`[...]` 는 링크 문법이다.** 대괄호로 묶은 평문이 링크로 해석되어 글자가 보이지 않을 수
  있다. 평문에는 쓰지 않는다
- 같은 층의 소제목은 **채번 여부를 통일한다.** `*설계 핵심*` 처럼 번호 없는 것과
  `*1) 대상*` 처럼 번호 있는 것을 섞으면 층이 어긋나 보인다

**두 파일 다 접지 않는다.** 문단 하나가 한 줄이다. JIRA 는 **단일 개행이 `<br>` 로
렌더링되므로** 폭을 맞춰 접으면 그 자리가 렌더링에 강제 줄바꿈으로 들어간다. 줄을 바꾸는
자리는 뜻이 있는 자리뿐이다 -- 문단 경계, 열거 항목, 표 행, 코드 블록 안.

**그래서 두 파일의 줄 구조가 같다.** 대조는 **줄 단위** 로 한다 -- 절 제목, 열거 항목의
개수, 표 행이 양쪽에서 맞는지 센다.

## 4. 쪼개기

**최대한 쪼갠다.** 이슈 하나가 커지면 본문이 길어지고 리뷰 범위가 넓어진다.
단계별/모듈별로 나누고, 각 이슈가 혼자 읽히게 만든다.

**서로를 언급하지 않는다.** `design`, `test`, `issue`, `pr` 어디에서도 다른 이슈 번호를
의존 관계로 쓰지 않는다. 예외는 **증거의 출처** 다 -- 여러 이슈가 함께 들어간 빌드에서 잰
것이라면 그렇게 밝혀야 하고, 숨기면 귀속이 더 틀어진다. 같은 배경을 여러 이슈가 필요로 하면 각자 자기 문서에 필요한 만큼 다시 쓴다.
리뷰어는 이슈 하나만 열어 볼 수 있어야 한다.

## 5. design_*.md 의 뼈대

**번호가 아니라 순서다.** 변경이 하나인 이슈와 넷인 이슈는 절 수가 다르다. 아래 순서를
지키고, 해당 없는 것은 절을 만들지 않는다.

```
대상 코드              바꾸는 자리의 구조. 규약을 먼저 세운다
문제                   2.1, 2.2 ... 문제마다 하나씩
변경 N                 변경마다 한 절. 결정 -> 구조 -> 왜 이 형태인가 -> 실패 처리
기존 구조를 바꿔도 되는 근거    (기존 규약을 건드릴 때만)
안전성 근거            코드로 답한다. 마지막에 요약 표
영향 범위 / 동작이 달라지는 지점
성능                   측정치는 전부 여기
```

**동작이 달라지는 지점이 없으면 그 절을 만들지 않는다.** "없음" 한 줄짜리 절은 자리만
차지한다. 대신 안전성 요약 표에 한 행으로 남긴다.

**측정하지 않았으면 성능 절에 그렇게 쓴다.** 절을 빼지 않는다 -- 읽는 사람이 빠뜨린 것인지
잴 것이 없는 것인지 알 수 없다. 무엇을 재지 않았고 왜 안 쟀는지, 재려면 무엇이 필요한지를
적는다. 구조적 비효율만으로 만든 이슈라면 없앤 연산이 근거이고 수치는 필요 없다.

### 5.1 문제 절은 해결 여부를 함께 말한다

문제만 서술하고 끝내면 **이 브랜치에 남은 결함** 으로 읽힌다. 문제마다 어느 변경이
고치는지 밝히고, 문제가 여럿이면 절 머리에 **문제 -> 변경 대응표** 를 둔다.

### 5.2 기존 구조를 바꾸는 근거

**"왜 기존 구조를 바꿔도 되는가" 를 코드로 답한다.** 오래된 구조를 건드릴 때 리뷰어가
가장 먼저 묻는 것이고, 추측으로 답하면 거기서 막힌다. 답하는 방법은 이렇다.

- 그 구조가 실제로 무엇을 하고 있었는지 코드에서 읽어낸다. 공유처럼 보이던 것이 실은
  소유자별로 걸러지고 있었다면, 그 필터가 근거다
- **하지 않는 것도 밝힌다.** "동시성 때문일 것" 같은 짐작이 남아 있으면 리뷰가 거기서 멈춘다.
  아니라는 근거를 코드로 댄다
- 도입 근거를 찾지 못했으면 **찾지 못했다고 쓴다.** `git log -S` 로 어디까지 찾았는지 적는다

**기존 절차를 지우지 않는 변경이면 그것을 명시한다.** 앞에 판정을 하나 두고 통과하지
못하면 원래 코드가 그대로 실행되는 형태라면, 정당화 대상은 "무엇을 없앴나" 가 아니라
"지름길의 결론이 기존과 같은가" 다.

## 6. test_*.md -- 어디를 어디까지 테스트할지

**설계 안내만 담는다.** TC 를 쓰는 사람이 어디를 찔러야 하는지 코드와 개념에서 짚어 준다.
케이스 파일 목록과 케이스별 의도는 `tc/README.md` 가 갖는다.

**내가 무엇을 했는지는 쓰지 않는다.** 돌린 날짜, 쓴 빌드, 몇 개가 통과했는지, 잰 수치,
"이번에 쓴 스크립트에는 그 단계가 없었다" 같은 회고 -- 전부 이 문서가 아니다. 실행할 때마다
낡고, 읽는 사람이 알고 싶은 것은 **무엇을 테스트해야 하는가** 다. 같은 사실을 규칙으로 바꿔
적을 수는 있다 -- "3회로는 구별되지 않다가 10회에서 드러나는 차이가 있다" 는 남기고,
"3회 재봤더니 안 나왔다" 는 뺀다. 측정 수치는 `design` 의 성능 절이 갖는다.

**부분집합인 형태는 축으로 세지 않는다.** 어떤 형태가 다른 형태가 이미 밟는 상태만
밟으면 별도 항목이 아니다. 갈래가 어떤 조건으로 갈리는지 코드에서 확인하고, 그 조건의
상태를 다 밟는 최소 형태만 남긴다. 뺀 것은 왜 뺐는지 한 줄로 적는다 -- 안 적으면 다음
사람이 빠졌다고 보고 다시 넣는다.

**기능과 성능을 나누고 기능을 앞에 둔다.** 성능 개선 이슈라도 잘못되면 **결과가 달라지는
것** 으로 나타나므로, 바뀐 코드가 같은 결과를 내는지가 먼저다. 성능 절은 그 이슈의 목적
자체를 확인해야 할 때만 두고 뒤에 붙인다.

**같은 층의 산출물 문서 이름을 쓰지 않는다.** `..._design_*.md`, `..._test_*.md`,
`..._issue.md`, `..._issue.jira` 처럼 이 묶음의 다른 문서를 서로 가리키지 않는다. 각 문서는 혼자 읽혀야
하는데, 서로를 가리키면 하나만 받은 사람이 읽을 수 없다. 문서 이름은 시각이 붙어 자주
바뀌므로 가리킨 쪽이 먼저 낡는다.

**테스트 케이스와 스크립트 이름은 적는다.** 케이스 파일, 측정 드라이버, 재현 스크립트,
소스 파일이 그렇다. 이것은 md 문서가 아니라 **돌리는 것** 이고, 첨부에 같이 들어가므로
읽는 사람이 실제로 가지고 있다. **실행 절차도 함께 적는다** -- 이름만 남기고 실행 순서를
지우면 파일을 가진 사람도 무엇을 먼저 돌릴지 알 수 없다.

가르는 기준은 문서인지 아닌지다. **같은 층의 산출물 md 면 빼고, 돌리는 것이면 적는다.**

예외가 둘 있다. 둘 다 **본문이 아니라 안내 자리** 다.

- **이슈 머리말** (3절). `---` 위이고 JIRA 본문에 들어가지 않는다. 어느 문서가 첨부인지,
  `deferred` 가 어디 있는지를 여기서 가리킨다. 이 자리가 없으면 묶음의 구성을 알 수 없다
- **테스트케이스 README** (1절). 어느 축을 덮고 어느 축을 못 덮는지 적으려면 축이 정의된
  문서를 가리켜야 한다. 다만 **절 번호가 아니라 축 이름으로** 대응시킨다

본문에서 빼는 것은 서술 중간에 다른 문서를 근거로 대는 것이다. 그것이 있으면 문서 하나만
받은 사람이 근거를 확인할 수 없다.

**시나리오는 길이에 따라 다르게 적는다.** 짧으면 전체를 적고, 길면 **어떤 구조로 테스트해야
하는지** 만 적는다 -- 무엇을 반복하고, 무엇을 바꿔 가며, 무엇을 매번 되돌려야 하는지.

담을 것:

- **이 변경으로 깨질 수 있는 것.** 위험을 먼저 말한다. 그것이 테스트의 목적이다
- **그 위험을 자극하는 입력의 축.** 타입, 길이, 경계값, 개수, 문자셋, 동시성, 실패 주입 중
  무엇을 흔들어야 하는지
- **축마다 왜 그것이 축인지.** 코드의 어느 분기가 그 축으로 갈리는지 적는다. 근거 없이
  나열하면 QA 가 어디까지 넓혀야 하는지 알 수 없다
- **무엇으로 판정하는지.** 결과 비교로 부족하면 무엇을 봐야 하는지 (텍스트, 카탈로그,
  통계, 로그)
- **테스트하기 어려운 축과 그 이유.** 재현 환경이 필요하거나 관측 경로가 없으면 그렇다고
  적는다. 테스트 범위를 정하는 사람에게 필요한 정보다

절마다 **의도 / 방법 / 판정** 세 줄을 고정한다.

## 7. deferred_*.md -- 접은 다른 방향

같은 문제를 푸는 방향이 A 와 B 로 갈렸고 A 를 골랐을 때, **B 를 여기 남긴다.**
B 가 없으면 이 파일도 없다. 선택 사항이다.

"다른 방향" 이라는 것은 접근이 근본적으로 다르다는 뜻이다. A 의 변형이나 A 를 하면서
같이 고칠 수 있는 것은 여기가 아니라 `design` 에서 다룬다.

B 를 접는 이유는 대개 셋 중 하나다. 무엇이든 **접은 이유를 수치나 범위로** 적는다.

| 이유 | 적을 것 |
|---|---|
| 고칠 곳이 너무 많다 | 몇 개 함수/호출부인지 |
| 영향 범위가 크다 | 어떤 계약/수명 규약이 바뀌는지 |
| 미해결 위험이 남는다 | 무엇이 해결되지 않았고 무엇이 필요한지 |

담는 것:

- B 가 무엇인가 -- **다시 시작할 수 있을 만큼** 적는다. 계약, 범위, 기대 이득, 막힌 곳. A 와 같은 분량일 필요는 없다
- 왜 접었나 -- A 와 B 의 이득을 같은 잣대로 비교한다. 비교에 필요한 만큼의 A 만 끌어온다
- **검토에서 깨진 전제** -- 있으면 절 하나로 남긴다. 없으면 다음 사람이 같은 가정에서 다시 출발한다

담지 않는 것:

- A 의 정당화. 그건 `design` 이다
- B 를 접었으니 A 가 옳다는 논증. 접은 이유만 적는다

제목 바로 아래, 배경보다 먼저 상태와 결론을 박는다.

```
*상태: 보류. 코드 읽기 + 외부 검토를 마쳤고 구현/측정은 하지 않았다.*
*결론 -- 지금은 하지 않는다. 이득이 X 인데 비해 Y 를 새로 만들어야 하고 Z 가 미검증이다.*
```

**`design` 에 B 의 조각을 남기지 않는다.** 조각으로 남으면 리뷰어가 A 의 일부로 읽는다.
B 를 재는 데 필요했던 배경 분석까지 함께 옮긴다.

첨부하지 않는다. 이슈 머리말에서 한 줄로 가리킨다.

## 8. 자주 하는 실수

### 문서 구조

| 증상 | 고치는 법 |
|---|---|
| **한 문서 안에서** 같은 사실이 3~4번 반복 | 사실별로 등장 횟수를 세어 본다. 자리는 하나로 정하고 나머지는 지운다. 문서 **사이의** 반복은 계층이라 정상이다(2절) |
| 두 절이 같은 논증을 두 번 | 합친다. 근거를 먼저, 표를 요약으로 |
| 한 절이 문서의 3분의 1 | 결정 / 구조 / 왜 이 형태 / 실패 처리로 소절을 나눈다 |
| 하지 않는 설계 논의가 섞임 | `deferred_*.md` 로 옮긴다 |
| 변경 갈래 수가 문서마다 다름 | 2절의 갈래 세기 규칙을 본다 |
| 목록이 길게 나열됨 | 2절의 목록 묶기와 깊이 규칙을 본다 |

### 도식과 표

| 증상 | 고치는 법 |
|---|---|
| 표를 코드 블록에 공백 정렬 | 마크다운 표로. 값이 바뀔 때마다 다시 정렬할 일이 없어진다 |
| 도식 안에 설명 문장 | 도식은 구조만. 설명은 아래 산문이나 표로 |
| 도식 라벨이 한글 | 라벨은 영어/ASCII, 한글 설명은 아래에 (`-` `\|` `+` `>` `<` `/` `\` 만 사용) |
| 메커니즘 설명에 `before/after` | 독자가 개선을 찾는다. `확장 전/후` 처럼 무엇의 전후인지 쓰거나, 아예 단계로 쓴다 |
| 갈래가 있는데 한 갈래만 그림 | 갈래를 다 그린다. 보통 안 그린 쪽이 문제의 원인이다 |
| 두 경로가 만나는 것을 표로 그림 | 호출 스택으로 그린다. "결국 같은 함수에 닿는다" 는 표로는 안 보인다 |

### 문장

| 증상 | 고치는 법 |
|---|---|
| 하드랩 | 두 파일 다 접지 않는다. 문단 하나가 한 줄 |
| 비유어 | `tight-comments` 6절 표 |
| 검증 안 한 것을 단정 | 근거의 출처를 쓴다 -- "근거는 코드 읽기다. 실제로 태워 본 측정은 없다" |
| 같은 낱말이 두 대상을 가리킴 | 수식어를 붙여 가른다. 앞에서 붙였으면 뒤에서도 붙인다 |
| 절 제목이 내용을 안 말함 | "추가 사정" 처럼 뭔가 더 있다고만 하지 말고 그 절이 하는 일을 쓴다 |
| 움직이는 식별자를 적음 | merge-base 나 브랜치 tip 의 SHA 는 develop 이 움직이면 낡는다. "merge-base" 처럼 관계로 적는다. 단 **측정에 쓴 build 는 SHA 로** 적는다 -- 그것은 낡지 않는 역사적 사실이다 |
| 같은 층 소제목의 채번이 섞임 | 채번 여부를 통일한다 |

### 절차

| 증상 | 고치는 법 |
|---|---|
| 임의 커밋 | 커밋은 사용자가 명시적으로 시킬 때만 |
| JIRA 첨부 덮어쓰기 시도 | 같은 이름이 중복 등록된다. 지우고 올린다 |
| 파일명 바꾼 뒤 참조 방치 | `.answer`, `tc/README.md`, 표 안의 백틱 참조까지 훑는다 |
| 문서만 보고 정합성 판단 | 패치와 원본 코드를 열어 확인한다. 문서가 코드보다 자주 틀린다 |

## 9. 외부 검토

큰 구조 변경을 제안하는 문서는 **전제를 깨 보는 검토** 를 한 번 받는다.
스스로 쓴 문서는 전제를 다시 읽지 않는다.

검토자에게 넘길 때 이렇게 묻는다.

- 이 문서가 참이라고 가정한 것 중 거짓인 것이 있나 (반례를 file:line 으로)
- 위험 목록이 완전한가
- "나빠지지 않는다" 류의 주장이 실제로 어디까지 참인가

받은 것은 **항목별 판정** 으로 정리한다. 산문으로 두면 무엇이 결론인지 남지 않는다.

| 항목 | 판정 |
|---|---|
| 방향 자체 | 유효 |
| 전제 <이름> | **거짓** -- 반례 N건, file:line |
| "...는 나빠지지 않는다" | 참인 범위를 좁혀야 함 |
| <미해결 항목> | 해결책이 정해지지 않음 |

## 10. 점검 절차

**뜻을 먼저 보고 형식을 나중에 본다.** 논리가 틀리면 문장을 다시 써야 하므로, 형식부터
다듬으면 그 일이 헛수고가 된다.

### 뜻 -- 사람이 판단한다

1. **패치를 열어 문서의 서술과 대조한다.** 이름/개수/조건은 코드에서 세어 본다. "호출부
   다섯 곳" 같은 수는 코드가 바뀔 때마다 낡으므로, 논지가 정밀도에 기대지 않으면 수를 뺀다
2. **주장의 범위가 근거보다 넓지 않은지 본다.** "모든", "언제나", "전부", "~뿐이다" 가
   나오면 그 자리에서 근거를 다시 확인한다
3. **덮는다고 적은 것이 실제로 덮는지 코드로 확인한다.** 호출부가 막고 있어 함수에 들어가지도
   않는데 확인한다고 적는 일이 생긴다. **이 주장이 틀리면 그것을 근거로 뺀 항목까지 함께
   틀린다** -- 커버리지 주장은 다른 결정의 근거가 되므로 혼자 틀리지 않는다
4. **문제 -> 변경 -> 테스트가 짝을 이루는지 본다.** 문제 수와 변경 수가 다르면 어디서
   합쳐졌는지 문서가 말해야 한다
5. **상세도 계층을 확인한다 (2절).** `pr` 에만 있는 동작 주장이나 안전성 주장이 없어야 한다.
   한 곳에서 고친 주장은 그 핵심 낱말로 네 문서를 다시 검색한다
6. **단정에 조사 범위가 붙어 있는지 본다.** "그런 경우는 없다" 는 어디를 어떻게 찾았는지
   함께 적혀야 재현된다
7. **다른 해결 방향이 섞여 있으면 `deferred` 로 뺀다 (7절).**
8. **문장이 어려운 곳을 본다** (`누가 읽는가` 표). 수량 지시어는
   `(두|세|네|다섯|둘|셋|넷)\s*(가지|경우|갈래|형태|곳|단계)` 로 후보를 좁혀 하나씩 본다
9. **반복되는 사실을 센다.** 3회 이상이면 자리를 하나로 정한다

### 형식 -- 기계로 훑는다

10. 한글과 ASCII 가 아닌 문자가 있는지 센다
11. 코드 블록에 언어 지정이 있는지, 한글 뒤에 정렬할 열이 오는지 본다
12. `_issue.md` 와 `_issue.jira` 가 하드랩돼 있는지 본다
13. `_issue.md` 와 `_issue.jira` 를 **절 단위로 대조한다.** 첫 절의
    `h2. *Description*` 은 JIRA 필드 제목과 겹쳐 생략하는 것이 정상이고, 나머지 절 제목은
    양쪽에 다 있어야 한다. **줄 구조는 양쪽이 같다** -- 열거 항목의 개수와 표 행을 세어
    맞는지 본다
14. 파일명/참조가 규칙에 맞는지 본다. 디렉터리 이름을 바꿨으면 그 경로를 적은 README 의
    실행 명령까지 다시 본다
15. `test` 에 실행 기록이 남아 있는지, 기능 절이 성능 절보다 앞인지 본다. 파일 이름은
    6절의 경계로 판정한다 -- 케이스와 스크립트 이름은 남아 있어도 된다
16. `pr` 의 `Remarks` 를 코드 주석과 대조한다. 주석에 이미 있는 것은 뺀다
17. 목록 항목 사이에 빈 줄이 섞여 있는지 본다. 한 문서 안에서 같아야 한다
18. `_issue.jira` 는 아래 마무리 점검을 돌린다. 눈으로는 안 보인다

### _issue.jira 마무리 점검 -- 세 가지만 기계로 훑는다

`_issue.jira` 는 **붙여넣기 전에 이 점검을 돌린다.** 깨진 문법은 MD 로 읽으면
정상으로 보이고 JIRA 에 올린 뒤에야 드러난다.

**이것은 JIRA 문법 검사기가 아니다.** 3절이 든 함정 가운데 기계로 셀 수 있는 셋만 본다 --
`{{...}}`, `**bold**`, 굵게 바깥의 글자. `-취소선-`, `_기울임_`, `+삽입+`, `^윗자리^` 의
짝, `\|\|` 표의 열 수, `#` 목록 사이의 빈 줄, `h2.` 위의 빈 줄은 **보지 않으므로 눈으로
확인한다.**

```sh
python3 - <<'EOF' cbrd-#####_issue.jira
import re, sys

# JIRA 는 `*` 를 목록 기호로도 쓰므로 줄 앞의 기호를 먼저 뗀다.
# 떼지 않으면 목록 기호가 굵게 여는 별표로 짝지어져 거짓 양성이 쏟아진다.
MARKER = re.compile (r'^[ \t]*(?:[*#]+|-|h[1-6]\.|bq\.)[ \t]+')
FENCE = re.compile (r'^\{(code|noformat)[:}]')

verbatim = False
hits = 0
for ln, raw in enumerate (open (sys.argv[1], encoding='utf-8'), 1):
    line = raw.rstrip ('\n')
    if FENCE.match (line.strip ()):
        verbatim = not verbatim
        continue
    if verbatim:                      # {code} 와 {noformat} 안은 원문 그대로 나온다
        continue
    line = MARKER.sub ('', line)
    if '{{' in line:
        print (f'{ln}: 미지원 문법 {{{{ }}}}')
        hits += 1
        continue
    if '**' in line:
        print (f'{ln}: 마크다운 굵게 ** 는 그대로 출력된다')
        hits += 1
        continue
    stars = [m.start () for m in re.finditer (r'(?<!\\)\*', line)]
    for i in range (0, len (stars) - 1, 2):
        o, c = stars[i], stars[i + 1]
        b = line[o - 1] if o else ' '
        a = line[c + 1] if c + 1 < len (line) else ' '
        if re.match (r'\w', b) or re.match (r'\w', a):
            print (f'{ln}: 굵게 미적용 -- {line[o:c + 1]}')
            hits += 1
            break
print (f'걸린 자리: {hits}')
EOF
```

**`_issue.jira` 만 넣는다.** `_issue.md` 는 `**bold**` 를 정상으로 쓰므로 함께 넣으면 전부 걸린다.

**출력이 비어야 넘긴다.** 걸린 자리는 굵게 할 범위를 어절 끝까지 넓히거나 문장을 나눠 고친다.

못 잡는 것을 알아 둔다. 표 셀 안의 별표는 목록 기호인지 글자인지 가리지 않는다.

### 최종 확인 -- 축 일곱

넘기기 전에 **축마다 따로 한 번씩** 훑는다. 한 번에 다 보면 형식이 눈에 걸려 뜻을 놓친다.
판정 방법은 위와 앞 절들이 이미 갖고 있으므로, 이 표는 축과 그 자리를 짝지어 준다.

| 축 | 판정 자리 |
|---|---|
| 사실 확인 -- 실제 변경 내용이 맞나 | 뜻 1, 3. 이름/개수/조건/파일 위치를 **실제 diff 에서** 센다 |
| 내용 오류 | 뜻 1. 코드에 대고 확인할 수 있는 서술을 먼저 본다 |
| 논리 오류 | 뜻 2, 6. 근거보다 넓은 주장과 조사 범위 없는 단정 |
| 논리 일관성 | 뜻 4, 5. 문서 사이의 개수와 핵심 주장이 어긋나는지 |
| 용어 일관성 | 8절 `문장` 표. 같은 대상을 두 낱말로 부르거나 한 낱말이 두 대상을 가리키는 자리 |
| 외부 파일 참조 | 6절의 경계. 같은 층의 산출물 md 이름만 빼고 케이스와 스크립트는 남긴다 |
| 배포용 적합성 | `품질 기준` 절의 실격 표 |

이 절이 더하는 것은 하나다. **한 번으로 끝내지 않는다.** 고친 뒤 같은 축으로 다시 훑는다 --
고치는 과정에서 새로 틀리는 일이 실제로 생긴다. 그리고 마지막 한 바퀴는 9절이 묻는 방식으로
남에게 맡긴다.
